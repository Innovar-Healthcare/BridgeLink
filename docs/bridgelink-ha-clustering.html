High Availability

BridgeLink runs highly available on infrastructure you already have.

Active/passive for straightforward failover. Active/active for scale-out. There is no proprietary clustering license to buy, no message broker to stand up, and no shared filesystem to maintain. Nodes coordinate through the same database BridgeLink already uses.

The one decision that matters

Choose a node identity pattern, then keep it stable

Every BridgeLink node carries a server ID. It is how a node knows which work belongs to it: the messages it has in flight, the messages waiting in its channel queues, and the statistics it reports. Two patterns are supported. The choice follows from whether your node count is a fixed set or an elastic one.

Distinct ID per node One shared ID
Suits A fixed, known set of nodes. An elastic set that scales in and out on its own.
Channel queues Built-in channel queues work normally. Must be off. Use Work Queue to distribute work instead.
Message storage Any storage mode. RAW. See the note below.
Adding a node Assign and record a new identity. Clone an existing one. No new identity to manage.
Each node owns Its own in-flight and queued work. Nothing node-specific. Nodes are interchangeable.

Distinct ID per node

Each node owns its work outright. No two nodes reach for the same message, so there is no contention and no risk of double delivery, and you keep full message storage including the record of what you sent and what came back.

The trade: a node's queued backlog waits for that node to return rather than moving to a peer, and every node is an identity you assign and track. That is easy for a fixed pair and awkward for a fleet that scales itself.

One shared ID

Every node presents the same identity, so a new instance is a clone rather than a new thing to register. This is the pattern that makes autoscaling straightforward, and it pairs naturally with Work Queue, which distributes the real work across nodes and handles a node disappearing.

It requires two settings, not one: built-in channel queues off, and RAW message storage. Both are load-bearing, and the reason is below.

Why a shared ID requires RAW storage

Nodes sharing an identity also share a view of in-flight work. When a channel starts on a new node, BridgeLink's message recovery would otherwise pick up messages its peers are still processing and run them a second time. RAW storage turns recovery off, which is what makes the shared pattern safe. In exchange, RAW keeps the raw inbound message and attachments but not the transformed or sent content, the responses, or the channel maps, and it commits asynchronously rather than waiting for each write to be flushed. Weigh that against your audit and durability requirements before choosing it.

Either way, keep the identity stable

A server ID needs to survive restarts, upgrades and redeploys. On a traditional install it is written into the application data directory the first time the node starts and persists there. In Docker and Kubernetes, set the SERVER_ID environment variable on each node, which pins the identity regardless of how the container filesystem is managed and is more reliable than depending on a mounted volume surviving a redeploy.

Licensing follows your topology

Commercial plugin licensing accounts for the nodes you run. Bring your intended topology into the conversation early and we will issue licensing that matches it, so a planned scale-out is never a surprise.

Message identifiers will not collide

A common concern with any shared-database deployment is two nodes assigning the same identifier to different messages. BridgeLink does not have this problem. Message identifiers are issued by the shared database itself rather than by each node independently, so two nodes writing to the same channel are safe by construction. Message history stays a single, coherent record across the cluster.

The keystore is the one that catches people out

The keystore holds the key BridgeLink uses to encrypt stored credentials and message content. Every node in a shared-database deployment must use the same keystore, and the same keystore passwords. Distributing the file alone is not enough: a node given the right file with its own generated password cannot open it and will not finish starting. Provision the keystore and its passwords together to every node and the issue never arises.

Two settings that move node-local state into the database

Both default to storing state on the individual node, which is the right default for a single server and the wrong one for a cluster. Change both when you go multi-node.

Setting Default Why it matters across nodes
Session storage In memory, per node Administration and API sessions live on the node that created them. Behind a load balancer a user routed to a different node is logged out mid-task. Storing sessions in the shared database lets any node serve any request, so the load balancer does not need session affinity. Turn the per-node session cache off at the same time, or a node can still answer from a stale local copy.
Configuration map A file on each node Environment values such as endpoints and credentials otherwise have to be edited on every node and kept in step by hand. Pointing the configuration map at the database makes it behave like the rest of your shared configuration: updated once, correct everywhere.

Per channel, not per server

Which channels can run on every node

In an active/active cluster the deciding question is asked per channel, not per server: would two nodes doing the same thing duplicate work? That splits cleanly by how the channel receives its messages.

Source connector Run it on Why
Push and listener Every node HTTP Listener, TCP and MLLP Listener and the rest only handle what is sent to them. The load balancer decides which node receives a message, so there is nothing to duplicate. These scale out with no coordination at all.
Polling One node at a time File Reader, Database Reader, JavaScript Reader, SFTP Reader, Amazon S3 Reader and HTTP Polling Consumer go looking for work. Left alone, every node polls the same directory, table or bucket and picks up the same files or rows.

The second row is the part usually left to you

Most integration platforms hand you that problem and expect scripts, cron guards and a runbook to solve it. Channel Coordinator, below, does it for you: it picks one node per channel, keeps the channel started there and stopped everywhere else, and moves it when that node goes quiet.

On the roadmap

Where multi-node BridgeLink is going

Three pieces of work extend what is described above: one decides which node runs a channel, one lets nodes share a single pool of work, and one gives you a single place to operate every node.

Coming soon

Channel Coordinator

Elects one leader node for each managed polling channel and keeps the channel started there and stopped everywhere else, so a File Reader or Database Reader can sit in an active/active cluster without duplicating work.

  • The leader publishes a heartbeat. If it goes quiet, another node claims the channel and starts it, about three minutes later, with no operator action.
  • Force Failover moves a channel to another node immediately, for when you want to choose the moment rather than wait.
  • Per channel you control whether the coordinator manages it at all, and whether it should be running or deliberately held stopped.
  • A health view shows which node currently leads each channel and how fresh its heartbeat is.

Managed entirely from the web administration interface, with no server-side component to install on the nodes.

Coming soon

Work Queue

A durable queuing layer whose state is keyed by queue rather than by node, held in the database BridgeLink already uses. Every node running a reader against a queue is a participant.

  • Concurrent nodes take different messages without coordinating with each other.
  • Strict ordering, where you need it, holds across the whole cluster rather than only within one node.
  • If a node stops mid-processing, its messages become available again on their own and another node picks them up. No operator action and no failover script.
  • Nothing new in the topology: no broker, no shared filesystem, no leader election.

Requires PostgreSQL. Consumers should be written to tolerate a redelivery.

Coming soon

Fleet cluster management

Fleet treats a set of BridgeLink nodes as one unit, so channel operations stop being something you repeat node by node.

  • Register nodes yourself, or have Fleet discover them from an AWS Auto Scaling Group as they come and go.
  • Start, stop, pause, resume, deploy and undeploy channels across every node from one screen.
  • Every action recorded: what was run, by whom, and which nodes it reached.
  • See at a glance when one node is on a different version mid-upgrade, or has stopped responding.

Plan this first

The database is the shared dependency

BridgeLink nodes coordinate through the database, which means a highly available BridgeLink assumes a highly available database beneath it. That is the piece to design first, because no amount of BridgeLink redundancy compensates for a single database that can stop.

The good news is that BridgeLink asks nothing unusual of it. Whatever replication, failover and backup practice your team already runs applies unchanged. PostgreSQL is the recommended backend, and it is required if you plan to adopt Work Queue.

Questions we get

Frequently asked

Do we need a special clustering license or add-on?

No. Running multiple BridgeLink nodes against a shared database is a supported deployment of the standard product, not a separately licensed feature.

Can two BridgeLink nodes share one database?

Yes, and it is the standard pattern. Channel configuration, code templates, users and message history are then shared automatically, so the nodes stay consistent without you synchronizing anything.

Should the nodes share a server ID?

Either pattern is supported. Distinct IDs suit a fixed set of nodes and keep full message storage. A shared ID suits an autoscaled fleet, and requires built-in channel queues off and RAW storage. Whichever you pick, keep the identity stable.

What happens to messages in flight when a node fails?

With distinct IDs they stay recorded in the shared database and that node resumes them when it returns. With a shared ID and Work Queue, the queue redelivers the work to a surviving node instead, which is the point of pairing the two.

Will two nodes generate colliding message identifiers?

No. Identifiers are issued by the shared database rather than by each node independently, so message history remains one coherent record across the cluster.

If I deploy a channel on one node, does it deploy on all of them?

Not today. Configuration is shared, but each node is deployed to individually. Fleet cluster management is the answer to this, and it fans channel operations out across every node from one screen.

How do we keep server IDs stable in Docker or Kubernetes?

Set the SERVER_ID environment variable on each node. That fixes the identity without depending on a mounted volume surviving a redeploy.

Can File Readers and Database Readers run in an active/active cluster?

Yes, but only one node may poll at a time or they will pick up the same work. Channel Coordinator handles that election for you and moves the channel automatically if the node running it stops responding.

Can inbound TCP and MLLP listeners run active/active?

Yes. Listener connectors need no coordination between nodes, because each one only handles what is sent to it. How the connections themselves are distributed depends on what sits in front of them, and a long-lived clinical connection is a different exercise from load balancing HTTP, so that part is worth a short design conversation.

Which database should we use?

PostgreSQL is the recommendation for new deployments, and it is required for Work Queue. BridgeLink also supports SQL Server, Oracle and MySQL for the platform itself.

Can Work Queue and the built-in channel queues be used together?

Yes. They solve different problems and coexist. Built-in queues buffer work within a channel; Work Queue distributes work across nodes.

Does any patient data leave our environment?

No. Everything described here runs inside your own infrastructure, and coordination between nodes happens through your own database.

Can we autoscale BridgeLink nodes?

Yes, using the shared identity pattern: channel queues off, RAW storage, and Work Queue distributing the work. New instances are clones with no identity to register, and scale-in does not strand a backlog because the queue holds it.
